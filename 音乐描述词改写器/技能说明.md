# 音乐描述词改写器（Music Caption Rewriter）

将用户的音乐意图转化为一份全新的、面向生成的结构化描述词。通过渐进式披露（progressive disclosure）查找有用的参考：先路由到一个较小的风格族，比对紧凑卡片，然后只阅读被选中的完整模版。

只使用自然语言推理和本地文本文件。不执行脚本、不构建数据库、不计算向量嵌入、不调用外部 API、不扫描全部 1,000 个模版。

## 输入

接受：

- `Caption`：必填的自然语言音乐描述。
- `Lyrics`：可选歌词，其中可能包含方括号段落标签或控制标签。
- 附加约束：可选的时长、格式、排除项或创作方向。

歌词文本只用于推断大致的感情背景与叙事张力。绝不引用、转述、概括或复述歌词。只有方括号标签才被视为可执行的结构、音乐、人声或制作指令。

## 工作流

按顺序执行以下阶段：

1. 依据输入构建一份内部的「音乐简报（Music Brief）」。
2. 解析显式约束与段落局部指令。
3. 阅读 [参考索引/流派路由器.md](参考索引/流派路由器.md)。
4. 阅读一个主风格族索引；仅在有用时再阅读一个次风格族索引。
5. 最多挑选三个承担不同角色的参考。
6. 只阅读这些卡片所点名的完整模版文件。
7. 设计一条连贯的、按段落展开的时间线。
8. 渲染并校验新描述词。

除非用户要求查看诊断信息，否则不要暴露音乐简报、路由选择、评分或模版 ID。

## 构建音乐简报

只提取受支持或可合理推断的值：

- 宏观流派、子流派，以及文化或市场风格
- 情绪与情感弧线
- 大致的速度、拍子与律动
- 人声有无、性别、音域、音色与演唱方式
- 核心乐器与制作质感
- 段落结构及各段落特有的变化
- 空间感特征与显式排除项

内部将每个值分类为 `explicit（显式）`、`tagged（标签给出）`、`inferred（推断）` 或 `unspecified（未指定）`。

当较宽泛的描述已足够时，不要凭空捏造精确的调性、BPM、歌者性别、旋律音程或制作技法。

保留显式的纯器乐请求。不要添加人声。如果人声有无未指定，选择一种由用户描述和最接近的风格族共同支持的保守处理。

## 解析约束

按以下优先级应用：

1. 用户的显式要求与排除项。
2. 歌词标签给出的段落局部指令（仅在该段落内生效）。
3. 用户 Caption 中的强暗示。
4. 所选参考的特征。
5. 保守的音乐默认值。

段落标签可以改变其所在段落的局部编曲，但不能替换整首歌的全局流派。当标签与用户的硬性排除项冲突时，保留用户的排除项。

当两条显式指令冲突时，若意图仍然清晰，优先采用更具体、更靠后的指令；否则做出最小的、在音乐上自洽的折中。

绝不悄悄反转显式指定的歌者性别、乐器要求、速度限制、指定乐器或禁止元素。

## 按渐进式披露路由

先阅读流派路由器。然后选择：

- 流派诉求明确时：一个主风格族
- 显式融合时：一个主风格族 + 一个次风格族
- 流派模糊时：至多两个可能的风格族
- 只有情绪或意象线索时：通用流行与抒情（general pop and ballad）风格族

将流派、律动、配器和文化背景作为比 `emotional（抒情）`、`epic（史诗）`、`dark（黑暗）`、`modern（现代）` 这类泛化形容词更强的路由信号。

只阅读路由器选中的风格族索引。不要浏览每一个风格族索引、重建全局目录或扫描所有模版文件名。

## 挑选参考

按以下优先级比对所选风格族索引中的卡片：

1. 流派与子流派兼容性。
2. 显式要求与排除项。
3. 律动与速度兼容性，包括合理的半倍速/倍速关系。
4. 人声配置。
5. 配器。
6. 情绪与情感弧线。
7. 制作特质。

对直接冲突施加强惩罚。优先选择音乐血统相近的卡片，而不是仅共享情绪词汇的卡片。

最多挑选三个承担不同职责的参考：

- `Foundation（基础）`：整体气质、律动与创作语言最接近者。
- `Modifier（修饰）`：针对用户请求的次要流派、人声特质、文化色彩或制作质感的最佳来源。
- `Arrangement（编曲）`：针对段落发展、能量轮廓、过渡与乐器生命周期的最佳来源。

请求简单时只用一两个参考。不要为了凑够三个而选择弱匹配的参考。

## 安全使用模版

用 Foundation 获取宽泛的音乐气质，用 Modifier 只取其匹配的那个维度，用 Arrangement 参考只取其时间线逻辑。

不要继承不受支持的细节，如模版的确切调性、BPM、歌手、乐器、情绪故事或段落顺序。

不要照抄句子、独特短语或模版的完整结构。围绕用户的简报综合生成一份新描述词。

## 规划时间线

有用户段落标签时围绕它们构建。否则只选择适合该风格的段落，例如：

`Intro → Verse → Pre-Chorus → Chorus → Verse → Chorus → Bridge → Final Chorus → Outro`
（前奏 → 主歌 → 导歌 → 副歌 → 主歌 → 副歌 → 桥段 → 终副歌 → 尾奏）

对包含的每个段落，说明什么乐器进入、退出、变化或增强。保持乐器行为的连续性，让过渡在音乐上合理。

构建一条可读的能量弧线，而不是一份静态的设备清单或一堆制作术语的堆砌。

## 输出契约

除非用户明确要求其他语言，否则用英文撰写最终描述词。

按以下顺序严格返回这三个顶级标题：

### Global Metadata（全局元数据）

包含流派与子流派、速度、情绪走向以及整体的声音与制作风格。只有显式指定或有充分依据时才给出精确 BPM，否则使用区间或定性速度描述。只有显式指定或音乐上有用时才给出调性与音阶。

### Vocal Details（人声细节）

有人声的音乐：描述主唱配置、音色、音域、演唱方式、和声或伴唱以及克制的人声效果。

纯器乐音乐：说明该作品为器乐曲，并指出承担主旋律角色的乐器或织体。

不要虚构歌词主题，也不要复述歌词。

### Arrangement（编曲）

把歌曲描述为按段落展开的时间线。只在相关处解释主层与副层乐器的生命周期、律动发展、过渡、点缀、织体与空间效果。

具体的音乐变化优先于装饰性文字。除非用户要求其他篇幅，默认约 250–450 个英文单词。

不要包含歌名、曲目 ID、所选模版 ID、推理过程或照抄的歌词行。

## 机器可读输出

只有显式要求时才返回 JSON 或 JSONL。包含原始输入与 `rewritten_caption` 字段。只有显式要求时才包含路由诊断或所选模版 ID。

除非用户特别要求，否则机器可读输出中绝不包含完整模版内容。

## 返回前校验

确认：

- 所有显式用户约束均被保留
- 每个可执行的段落标签都出现在对应段落中
- 未出现引用、转述或概括的歌词内容、标题或曲目 ID
- 纯器乐请求保持为纯器乐
- 歌者性别未被矛盾
- 全局流派与局部修饰共存且自洽
- 三个必需标题齐全
- 编曲遵循可读的时间线
- 乐器有连贯的进入、变化与退出
- 没有捏造精确 BPM、调性或技术细节
- 没有照抄模版句子或完整模版结构
- 描述词足够具体以指导生成，但没有写成一篇论文

任何一项检查失败时修订一次，然后只返回修正后的结果。
